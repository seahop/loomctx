# Tying existing pipelines into LoomCtx (D-034)

Most pipelines end in a log shipper, a queue, or a scheduled export — not
custom code. LoomCtx meets them where they are:

| You have | Use | Code to write |
| --- | --- | --- |
| Fluent Bit, Vector, Logstash, Filebeat, OpenTelemetry Collector | their HTTP output → `POST /v1/ingest/batch` (JSON array or NDJSON); reshape records in the shipper's transform stage | a field mapping (`vector.yaml`, `fluent-bit.conf` + `to_loomctx.lua` here) |
| Kafka / Redpanda topics | `python -m loomctx.kafka_consumer` (compose profile `kafka`, k8s manifest) reads envelopes from your topics | none — point it at brokers + topics |
| Files / exports / cron jobs (any language) | `python -m loomctx.ingest --url … file.jsonl` or `--db` for direct writes | emit NDJSON envelopes |
| Custom code | Python SDK, TypeScript SDK, Go SDK (`sdk/`); anything else via `contracts/openapi.json` + your language's OpenAPI generator | a few lines |
| Public feeds (CISA KEV, NVD, EPSS) | `python -m loomctx.connectors.vulns load` — a connector: pull, map, register schema, ingest (`docs/real-data.md`) | none — the pattern for your own connector is in `src/loomctx/connectors/` |
| STIX 2.1 bundles (a TIP, MISP, OpenCTI, a vendor feed) | `python -m loomctx.connectors.stix import bundle.json` — relationships, sightings and object properties become cited, time-windowed claims; `export` writes the namespace back as a valid bundle (`docs/interop.md`) | none, or a `--mapping` JSON to rename predicates |
| OCSF `vulnerability_finding` events (scanners, cloud security hubs, SIEMs) | `python -m loomctx.connectors.ocsf import findings.ndjson` — host/CVE claims that join the KEV/NVD record; `export` writes findings back (`docs/interop.md`) | none |
| AI agents | MCP (stdio or streamable-http) | none |

Every path lands in the same append-only, cited, idempotent store. Give
each pipeline its own write-only key pinned to its `source`
(`docs/administration.md`) so a compromised shipper can't forge other
sources' facts.

## Generating a client for another language

```bash
docker run --rm -v "$PWD:/local" openapitools/openapi-generator-cli:v7.10.0 generate \
  -i /local/contracts/openapi.json -g java   -o /local/build/loomctx-java     # or: csharp, go, rust, kotlin, php, ruby, swift5
```

`contracts/openapi.json` is regenerated by CI from the running app and
checked for drift, so a generated client is always current.
